# Phase 1.2: installed Codex adapter and effective configuration

Implementation ticket: [#20](https://github.com/michaelahoff/content-kanban/issues/20). Parent release: [#18](https://github.com/michaelahoff/content-kanban/issues/18). Contracts: [completed specification](https://github.com/michaelahoff/content-kanban/issues/12#issuecomment-6041712115), [configuration policy](https://github.com/michaelahoff/content-kanban/issues/16#issuecomment-6041007114), [native isolation findings](https://github.com/michaelahoff/content-kanban/issues/17#issuecomment-6041470327), and ADR 0001.

This is the adapter/configuration foundation. Card chat, durable submission/attempt rows, the worker, protected card tools, image import/adoption and recovery UI belong to #21–#25. Phase 1 remains unreleased. No provider API fallback or target substitution is implemented.

## Boundaries

`codex-adapter.js` owns one lazy `codex app-server` child per application. Initialization, correlated RPCs, thread-scoped ordered notifications, dynamic tool dispatch, user approval/input requests, interruption, imageGeneration provenance and read-only paged history use the installed protocol. It rejects path/history replacement when resuming. Native thread ID, workspace and provider must match. Every turn supplies the chosen model explicitly. Listed models are checked without guessing a default; account access errors still fail at native dispatch. A reroute blocks further work and attempts interruption.

Callbacks return protocol responses or retain a request's `respond` closure for later user input. Stop, terminal events and process exit invalidate those closures. Missing handlers deny actions. Process failure rejects outstanding RPCs and emits a thread-scoped exit event. It never automatically repeats a submission. A turn-start timeout retains the busy fence because delivery is uncertain. A restarted process requires exact reopen before another turn.

History reads use `thread/read` (metadata), `thread/turns/list` with **full** items and cursors, and `thread/items/list`. They never call resume or initiate a turn. Summary-only turn pages omit user client IDs and are inadequate for delivery reconciliation. Image notifications preserve the actual native item ID, turn/thread ID, result bytes/base64, saved path, status and revised prompt; this module neither imports an image nor calls it adopted.

`codex-configuration.js` compiles selections into deeply frozen, content-addressed snapshots. Include the entire snapshot with each future submission, rather than reconstructing it from mutable settings. Persist the returned native binding receipt with the conversation: provider, exact thread ID, workspace and effective configuration ID. A configured resume requires that receipt and rejects a changed configuration even after app restart when the adapter has no in-memory record. Its native options exclude project AGENTS, disable all discovered native skills and disable apps/plugins/hooks/MCP in thread configuration. Disabling a flag alone does **not** establish isolation: the gate also blocks any discovered MCP/plugin/hook setup because exact exclusion and every dispatch path remain unproven. Native skill selection remains unavailable; developer instructions and explicitly selected global AGENTS guidance are supported in the tested ordinary shape.

Global native AGENTS cannot be excluded by `project_doc_max_bytes`; an unselected global source makes the configuration unavailable. Selected global guidance is pinned by path and content hash. Native instruction sources and the workspace-write/on-request/user approval baseline are checked after open and before submission. A mismatched result never authorizes dispatch. The configured production opener explicitly targets the installed `openai` provider; the loopback test provider is supplied only by the native test.

Before dispatch, refresh `configurationDiscovery(adapter, { cwd: cardWorkspace })` for the exact target workspace and call `queuedConfigurationDecision`. Removed/changed guidance, missing capabilities, newly discovered items, changed instruction hashes and changed harness versions hold the frozen configuration until explicit cancel/resubmit. A removal never rewrites the old snapshot. Changing native options on an existing adapter binding requires an explained, explicitly chosen **empty fresh context**. Warm resume or unsubscribe is not configuration-update proof. Cold resume receives the same frozen configuration overrides; it does not re-register dynamic tools (the resume schema has no such field).

Schema migration 6 adds one workspace-scoped `provider_configurations` row per provider with revision, desired selection and update time. Save uses revision conflict protection and records `configuration_changed` in the canonical activity log in the same transaction. There is no native work in a store transaction. Effective submission snapshots/holds will be persisted alongside submissions by #21; the queue decision here is the tested worker boundary, not an existing production queue.

The board links to `/codex.html`. Reading settings or saving selection starts no native process. Only explicit discovery starts Codex. Optional items start unchecked, unsupported items display reasons, selections survive reload, and the page discloses native permission and summary limits.

## Evidence on 2026-10-07

Installed harness: **codex-cli 0.160.1**. Node.js **22.17.1**. Schema generated with `codex app-server generate-json-schema --experimental` from that installation. Tests validate both request directions and method responses against it. A small draft-07 validator covers the generated structural keywords; this is not a general schema-validation library. Configuration support is gated to the verified native version.

- `npm test`: **66 passed**, five native cases intentionally skipped unless opted in. Nine transport cases cover deliberately reordered correlated replies, two concurrent isolated thread streams, exact cold resume/tool dispatch, explicit model changes and unavailable models, configuration replacement rejection, approval/input, Stop and late-response fencing, process failure, full paged reconciliation, native imageGeneration provenance, unavailable executable and uncertain RPC timeout. Configuration/store/server cases cover frozen snapshots, changed/new inventory holds, global guidance removal/content changes, unsupported native action sources, sandbox/source verification, SQLite reopen and revision conflicts, and idle settings without a native process.
- `npm run test:native`: **five passed**, using the actual installed app-server with a credential-free loopback Responses fixture and disposable CODEX_HOME/workspaces. `gpt-6-luna` and `gpt-5.6-luna` are explicit native model identifiers exercised through the fixture. These are registration, configuration, persistence, dispatch and history proofs, **not new account-entitlement or inference-quality proofs**. No credentials reach the fixture; no global config/authentication is changed.
- Native evidence includes persistent dynamicTools dispatch after unsubscribe/reload and SIGKILL/restart; exact two-card bindings and model change; two distinct instruction configurations on a shared process before/after crash; unselected skill/project guidance absent after restart; a newly discovered skill holding the earlier snapshot and remaining absent in explicitly revised fresh context; selected global guidance surviving cold resume and removal holding queued work without inference; full-history clientUserMessageId retention and paged item reads; missing rollout causing exact resume failure without a replacement thread or model request.
- `npm run test:browser`: full existing suite passed, including movement/undo/graphs/images and conflicted drafts. T3 collaborative browser additionally verified settings save/reload, no native process on opening, actual installed discovery with every optional item unchecked, truthful blocked reasons, and a 390px layout without horizontal overflow.
- The actual current native home discovers MCP/plugins. The page reports that configuration **unavailable** with named isolation reasons. Successful clean fixture gates do not enable that broader setup.

Observed caveats: a thread with no first turn has no persisted rollout and cannot necessarily resume after restart; metadata can outlive a removed rollout. Retained metadata alone proves neither native history nor non-delivery. Keep the exact binding native-unavailable and require the later explicit fresh-context/recovery flow. Unsubscribe can leave a thread loaded in the native process; its success is not unload or configuration-change proof. Reapplying frozen overrides on cold resume is necessary because those exclusions are not automatically restored from native history. Complete tool-free native summaries remain unavailable.

The official [Codex app-server documentation](https://developers.openai.com/codex/app-server) describes the transport/lifecycle. Installed schemas and bounded tests above determine this integration's actual version-specific behavior. Earlier [live native account evidence](https://github.com/michaelahoff/content-kanban/issues/13#issuecomment-6040301068) remains separate from this credential-free validation. Native image generation/editing, account limits, protected mutations, durable recovery and the cumulative Phase 1 release gates remain required in later milestones.
