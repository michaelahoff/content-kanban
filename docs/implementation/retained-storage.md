# Internal retained-storage foundation

Implements [#47](https://github.com/michaelahoff/content-kanban/issues/47) against the approved [project-assets specification](https://github.com/michaelahoff/content-kanban/blob/f7149d373a8c8284cdd6b046049d6d54a3c35c57/docs/specs/project-assets.md), storage portions of acceptance cases 20–22. The Library, native asset delivery/protection, archive and complete export/restore are subsequent tickets. No new HTTP routes or user workflow are exposed here.

## Boundary

`openStore()` exposes `store.retained`; all payload filesystem access by app features stays in `retained-storage.js`, with private SQLite operations in `store-retained.js`. The project Library (`library.js`, [notes](project-library.md)) publishes and reads only through `store.retained` and uses the metadata's read-only listing queries. The one exception is whole-workspace export/restore (`backup.js`, with read-only inventory SQL in `store.js` `inspectBackupDatabase` over the database snapshot), which copies the `retained/versions/` directory verbatim while it owns the data directory (data lock or maintenance) and verifies each payload against the version's recorded hash and size. Export never writes there; restore writes only into its private staging before one atomic activation into a new or empty directory ([workspace restore](workspace-restore.md)). Pass the existing workspace-scoped actor context. Operations require exclusive data-directory ownership, as the server/backup CLI already establish with `lockDataDirectory()`. Recovery finishes before `openStore()` returns and before the server starts its workers. Asynchronous retained operations belong outside `store.transaction()`.

- `publish(ctx, { operationId, projectId, kind, filename, objectId?, provenance? }, bytes, { signal }?)` imports a byte stream/async iterable or `Uint8Array`. Kinds are asset, document and output; they do not restrict formats. Encode authored text explicitly before publication. A replacement names the existing object; a new publication gets an independent identity. Filenames are version metadata and never authoritative paths.
- `publishBatch(ctx, [{ descriptor, source }], options?)` returns independent success/error outcomes. Stable workspace-scoped operation IDs make retries reuse successful versions without consuming their sources. Once the complete source digest is recorded, a failed-operation retry must match it. Before a complete stream exists, retry can restart that incomplete upload.
- `current`, `version`, `inventory` return metadata without authoritative filesystem paths. `remove` hides the source from current selection while retaining all versions. Ownership is project/workspace scoped; equal bytes never merge identities.
- `read(ctx, versionId)` verifies the entire committed original's SHA-256 and size before returning a bounded stream; it rechecks the streamed bytes too. The caller must consume or destroy the stream. Missing, changed or linked originals mark only that version unavailable.
- `peek(ctx, versionId, length)` returns a committed original's first bytes without verifying the whole file, for previews only; anything delivered is read verified.
- `materialize(ctx, versionId, workspace, relativePath, options?)` always builds a verified independent file under `data/workspaces/`, atomically replacing any stale/tampered copy. A historical version never follows the source's current version. Traversal, linked directories and authoritative destinations are refused.
- `copy(ctx, versionId, descriptor, options?)` publishes independent verified bytes into a new object, including a different owning project in the same workspace. Copy provenance records the frozen source version; a successful retry validates its operation metadata without rereading an unavailable source. `repair(ctx, versionId, bytes, options?)` accepts only the recorded exact SHA-256/size and preserves the object/version/provenance and current-version relationship.

## Publication and recovery

Append-only schema migration 14 adds retained objects and version/publication states without changing legacy image tables or `data/images/`. New bytes use random UUID names in private `data/retained/staging/` and `versions/` directories. Imports use backpressure; hashing, reads, writes and copies use bounded buffers without a type allowlist or initial file/project quota.

Publication records staging, streams/hashes complete bytes, flushes the file, pins the digest, atomically renames it, flushes both directory entries, records published state, and finally commits current-version metadata. No uncommitted version is readable. The current-version update checks the captured predecessor and removal state; a concurrent replacement/removal cannot commit stale work. Failure after metadata commit remains a success, including when acknowledgement is interrupted.

Startup removes owned incomplete staging/repair files and tracked noncommitted payloads, marking those operations retryable. It never collects committed versions by reference count, visibility, supersession or availability. Unknown files are left alone. Required originals are verified on use; a workspace edit cannot change them through a shared inode. Matching repair atomically replaces the bytes and restores availability without rewriting frozen historical identities.

Backup format 2 ([complete workspace export](workspace-export.md), #50) replaced the earlier refusal: every committed version, including superseded, removed and unavailable ones, is required coverage, streamed, checked against its recorded hash and size, and inventoried in the manifest. `retained/staging/` is temporary and excluded.

## Acceptance evidence

`node --disable-warning=ExperimentalWarning --test test/retained-storage.test.js` covers opaque/doc/output bytes, stable retries, disconnect/abort, independent batches, corruption/deletion, exact repair, frozen references, ownership, hardlinks/symlinks/path escapes, and safe legacy-backup rejection. Separate child processes terminate abruptly at staging, first write, flushed staging, byte publication, publication-state update and committed metadata; reopening proves only complete committed versions are selected. ENOSPC is injected at write/publication boundaries for the ordinary suite. `npm run test:retained-disk-full` additionally exhausts an isolated 16 MiB tmpfs in a Linux user/mount namespace; it checks the actual ENOSPC error, preserved current content, reclaimed staging, successful retry and restart. It requires Linux unprivileged user namespaces and never fills the shared host disk. Reclaiming staging before recording failure leaves space for SQLite journaling.

`npm run test:retained-large` processes 2,147,549,185 opaque bytes through import, independent materialization/copy, repair, restart and verified read. The 2026-10-08 run matched SHA-256 `62897f37e6c38ad8f92398cd16205c5879eb48dc4cf86e6452cc2640ac9a0780` and peaked at 130.25 MiB RSS. The script requires approximately 7 GiB free temporary space and asserts peak RSS below 256 MiB. Multi-GiB export/restore and native authoritative-write prevention are explicitly later-stage gates, not evidence claimed by this internal foundation.

The project is JavaScript without a configured typechecker; changed modules receive `node --check`, focused suites run during implementation, and `npm test` covers the full existing suite.

Parallel code-review results: Standards found no documented-standard breaches or substantive baseline smells; its materialization stream-leak finding was fixed and reproduction confirmed descriptor closure. Spec found a successful-copy retry dependency on an unavailable source; the regression was observed failing, fixed and confirmed passing. Both axes finished with zero unresolved findings.
