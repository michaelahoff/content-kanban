# Native Codex and Claude conversation contracts

Evidence collected 2026-10-06 for [Verify native Codex and Claude conversation contracts](https://github.com/michaelahoff/content-kanban/issues/2), a child of [Wayfinder: Frameboard card chats, native agents, and living history](https://github.com/michaelahoff/content-kanban/issues/1). Scope: personal, local harness integration; separate API services and production implementation excluded. This supplements [the prior T3 integration research](t3-code-card-chats.md), whose proposed chat organization and API fallback are superseded by the map.

## Finding

Both harnesses have structured contracts for independent, durable conversations. Codex exposes a bidirectional app-server protocol; Claude exposes the official Agent SDK over Claude Code. Neither a saved transcript nor a live process is the native conversation: Frameboard needs its own card/chat/run identities, an explicit native session binding, and preserved provider state. Native billing and permitted third-party distribution are distinct questions. No real-provider conversation or account entitlement was tested.

The most consequential new finding is that submitting during an active turn can modify that turn. Frameboard cannot infer a distinct queued run from a second submission. Stop also needs queue semantics: Claude's SDK interrupt does not cancel queued messages. [Codex turn implementation][codex-turn-processor], [Claude message priority and interruption][claude-typescript]

## Evidence and version baseline

Read-only checks found `/usr/bin/codex`, **codex-cli 0.160.1**, and `/usr/bin/claude`, **Claude Code 2.1.291**. The earlier report inspected Codex 0.160.0. `claude --help` confirms explicit resume/session IDs and structured input/output switches; it was not used to send a prompt. `@anthropic-ai/claude-agent-sdk` is not installed in this worktree. The public npm registry reported **0.3.292** as latest; this is a candidate to pin, not a tested compatibility claim. [Official SDK package][claude-npm]

`codex app-server generate-json-schema --out <temporary-directory>` succeeded without starting a conversation. The generated v2 bundle SHA-256 was `81a88c04ae4984b16d73080f4109d0477682bc76c8adbe483e371175ce54c054`. Default generation excluded experimental additions. Source cross-checks use the exact [Codex 0.160.1 tag][codex-tag], resolved to commit `d27764b82f7118f674371e6d6e76271d9d606edb`. This fingerprint identifies the observed artifact, not a supported compatibility range.

Only executable versions/help, generated protocol files, public package metadata, official docs, and first-party source were inspected. No credentials, private session transcripts, authentication mutation, model turn, paid request, SDK installation, or application change was involved.

## Codex

**Lifecycle and transport.** Launch the installed `codex app-server`; its default stdio transport is newline-delimited bidirectional JSON-RPC. Initialize each connection with client identity, acknowledge `initialized`, then create with `thread/start` or resume with `thread/resume(threadId)`. `turn/start` returns a turn identity. Server notifications carry turn/item progress; server requests require correlated answers. `turn/interrupt(threadId, turnId)` requests cancellation; final `turn/completed` distinguishes completed, interrupted, and failed. The documentation still warns that app-server is experimental and unsupported for production workloads, while distinguishing ordinary API fields from those gated by `capabilities.experimentalApi`. This is a pin-and-test integration, not an unconditional stability guarantee. [Official app-server guide][codex-app-server]

**Identity and streaming.** The installed schema includes `Turn.id`, `ThreadItem.id`, user-message `clientId`, and `TurnStartParams.clientUserMessageId`. Preserve the client submission ID as well as thread/turn/item IDs. JSON-RPC request IDs identify transport requests; they are not durable prompt receipts. Text deltas and completed text items, commands, file changes, tool results, and compaction are different event types. Reconcile final items with accumulated deltas instead of displaying them twice. The source defines image-generation items too; a text-only consumer would lose structured output. No inspected source establishes that a repeated `clientUserMessageId` is an exactly-once execution key. [Turn schema][codex-turn], [item definitions and mapping][codex-item]

**Submitting while busy.** The exact-version handler calls `start_or_steer_turn`, explicitly handles a `Steered` outcome, and can return the active turn ID. A second `turn/start` therefore must not be treated as a new queued graph run. `turn/steer` is an explicit alternative with expected-turn checking. Proposed product consequence, not a chosen architecture: keep automatic submissions pending in Frameboard until the native conversation is idle, reserving steering for an intentional user action. Independent threads remain independent conversations; native support supplies no promise of an account-wide concurrency allowance. [Implementation][codex-turn-processor]

**State.** Leave new chats durable (`ephemeral` false). Codex keeps local configuration/state beneath `CODEX_HOME`, normally `~/.codex`; authentication may be file-backed or OS-keychain-backed. Its rollout module stores replayable session histories and defines `sessions` and `archived_sessions`; thread listing also uses a state database. Preserve the native rollout/state environment and attachment files, not just Frameboard's display transcript. Do not equate `history.jsonl`, a general history file, with a complete per-thread backup. [State configuration][codex-config], [rollout recorder][codex-rollout], [rollout directories][codex-rollout-lib]

**Input, approvals, and capabilities.** The local schema accepts text, local images, and image URL/file identities; paths refer to the backend's filesystem. Models expose input modalities and effort choices. Server requests cover command/file/permission approvals, tool questions, and MCP elicitation. Bind every pending request to the correct native conversation/run; decline/cancel and resolved-request cleanup need representation. Unsupported/experimental requests need explicit handling. `model/list` and feature discovery are useful discovery surfaces, but their presence cannot prove account-specific image generation. Native `imageGeneration` carries status, result, saved path, revised prompt, transparency, and failure in this schema; importing output bytes remains app work. [Local-schema corroborating source: turns][codex-turn], [items][codex-item], [capability and approval guide][codex-app-server]

**Authentication.** Official documentation distinguishes ChatGPT subscription access from API-key billing and describes reuse of cached local CLI login with automatic token refresh. For this scope, let the installed runtime use its native authentication; no token extraction or alternative Responses/token-sharing configuration is necessary. A version check does not establish that the currently installed runtime is signed in, uses subscription authentication, or has available usage. Managed workspace restrictions can apply. [Authentication][codex-auth]

## Claude Code through Agent SDK

**Sessions and persistence.** `query()` accepts either a single prompt or asynchronous messages. Capture `session_id` from init/result, or supply a new UUID through `sessionId`; follow up using `resume: exactSessionId`, not `continue` (most recent). Persistence is enabled by default. Native transcripts live under `~/.claude/projects/<encoded-cwd>/`, or the corresponding `CLAUDE_CONFIG_DIR`. Current versions support cross-directory lookup, but native files must exist. Session persistence covers conversation, not restoration of card state or filesystem changes. A `SessionStore` can mirror native entries and subagent sidecars; it is not simply Frameboard's visible-message table. [Session guide][claude-sessions], [external storage contract][claude-storage]

**Live query and queue.** Streaming-input mode supports image content blocks, interactive permissions, ongoing input, and interruption. Although the mode guide summarizes sequential queueing, the detailed current contract is more specific: messages without a priority, or with `next`, may be consumed between tools in the active turn. `later` defers until a new turn; multiple pending messages can still be merged. UUIDs and `user_message_uuids` correlate merged messages. If Frameboard needs a distinct result per automatic graph prompt, app-level serial submission is the conservative contract. Do not run two writers against the same native session merely because independent sessions are supported. [Streaming input][claude-streaming], [message identities/priority][claude-typescript]

**Stop.** `Query.interrupt()` is available in streaming-input mode. The `interrupt_receipt_v1` capability enables a receipt of UUID-bearing messages still queued; these may run afterward. The SDK method never sends `cancel_queued`. Direct control-protocol clients can request cancellation only when `interrupt_cancel_queued_v1` is advertised. An empty receipt does not prove the queue is empty; messages without UUIDs are omitted. Keep undispatched Frameboard jobs cancelable independently and avoid blind resending after interruption. [Interrupt contract][claude-typescript]

**Messages and streaming.** `includePartialMessages: true` exposes `stream_event` blocks, including text and tool-input deltas. Complete assistant blocks may share one provider message ID, and arrive in addition to those deltas; retain block attribution and avoid duplicate display. Tool use/results, subagent attribution, compact boundaries, final result/error, and partial text all need preservation. Assistant `aborted` marks truncated output; `resume_reason` can distinguish a configured automatic interrupted-turn restart. `user_message_uuid`/`user_message_uuids` are useful associations, not documented execution deduplication guarantees. These versioned fields need fallback behavior for older CLIs. [Streaming output][claude-output], [typed messages][claude-typescript]

**Permissions, input, and runtime settings.** `canUseTool` pauses for tool permission or `AskUserQuestion` only when earlier permission rules have not already resolved the action. It is not a universal tool interceptor; hooks apply before that flow. Explicitly choose policy rather than assuming the default is manual. MCP elicitation uses `onElicitation`; unhandled requests are declined. The query supports model selection, `setModel`, `supportedModels`, initialization metadata, and open-set CLI capability flags. SDK releases bundle a native Claude Code binary by default; use `pathToClaudeCodeExecutable` deliberately to reuse the installed harness. Pin both SDK and actual launched CLI, since they can differ. [User input][claude-input], [typed options/query methods][claude-typescript]

**Subscription boundary: unresolved product permission, not missing protocol.** The current Help Center update says the announced June change remains paused and SDK, print-mode, and third-party-app use still consume subscription limits. Separately, the SDK overview/quickstart says developers may not offer claude.ai login or rate limits in third-party products without prior approval. These are different claims: billing describes usage accounting; it does not authorize distribution. Personal local reuse of an already-authenticated harness is the narrow path being investigated, and should not be represented as permission to distribute a subscription-backed product. Public sources do not settle the boundary for Frameboard; obtain provider clarification before making that product promise. A successful live turn would prove mechanics/account access, not resolve provider terms. The CLI's `--bare` mode specifically excludes OAuth/keychain authentication, so it is unsuitable for the intended subscription route. [Current billing notice][claude-plan], [SDK policy note][claude-overview], read-only installed `claude --help`.

## Extension contract and decisions this evidence enables

Suggested capabilities for any future installed harness: report executable/version, supported models and input/output modalities; create/resume an explicit native identity; submit an identified input snapshot; emit stable message/item associations and lifecycle events; interrupt with documented queue consequences; surface and answer approval/input requests; report errors/limits; describe native storage requirements and reconciliation after disconnect. Image outputs and file identities must remain structured optional capabilities. These are proposed requirements, not the final module interface.

An application chat can remain one per card while its native binding changes; switching harnesses cannot resume the other harness's native history. Context transfer, model-visible compaction, manual application of output, queue cancellation, and restoring cards while retaining conversations remain product decisions. Neither provider documentation supplies a transaction joining a SQLite card move to a model submission, nor an exactly-once replay guarantee after ambiguous delivery. A durable local intent record must not be mistaken for either guarantee.

## Minimal follow-up validation

**Read-only/no inference:** pin executable and SDK versions; regenerate/compare schemas; inspect supported contract fields; verify selected launch path and configured native storage location without reading secrets. Public docs/source/schema work is complete here. If a runtime handshake, model listing, or account check is added later, confirm whether it refreshes auth, starts background services, or modifies state before calling it read-only.

**Real provider use/native state writes, not performed:** for each harness, create two chats with distinguishable context; send/follow up and prove no cross-talk; send identified text plus an image; preserve text/tool events and final results; stop during streaming and during permission wait; verify queued-job cancellation and no unintended follow-on turn; restart and resume the exact session; exercise missing native-state and usage-limit failures. Test an app crash before and after provider acknowledgment and reconcile ambiguous delivery without automatic duplicate prompting. Check that installed authentication is subscription-backed without exposing credentials. The image round trip is separately researched; schema presence alone is insufficient.

**Authentication changes or provider clarification, not performed:** interactive sign-in only if needed and authorized; clarify Anthropic's personal-use/distributed-product boundary; recheck subscription notices at implementation/release time. No API fallback is proposed. A paid capability check or login operation should be a separately authorized task, never concealed inside report validation.
